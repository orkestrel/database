# Native-first audit of the `@orkestrel/database` family

Finding: the core is scan-first. It requires a driver to supply only keyed reads, one ordered `scan`, and `snapshot`, and it runs filtering, ordering, paging, counting, and guarding in JavaScript. A driver can override with `records`, `aggregate`, and `stream`, but the core then discards most of what that override could do: it never passes `limit` or `offset` to `records`, never calls the driver's native `count`, and runs a per-row guard over every returned row. Both drivers also decline pushdown on narrow grounds: SQLite pushes down all-or-nothing, and IndexedDB narrows by one range and walks the rest. The cost to an application is rows read per request that scales with matching rows (`M`) or table size (`N`) where the engine could read one page (`P`) or one number.

Citation key: `core` is `node_modules/@orkestrel/database/dist/src/core/index.js`, `sqlite-driver` is `.../database/dist/src/server/index.js`, `idb-driver` is `.../database/dist/src/browser/index.js`, `dts` is `.../database/dist/src/core/index.d.ts`, `idb-wrapper` is `node_modules/@orkestrel/indexeddb/dist/src/browser/index.js`, `sqlite-wrapper` is `node_modules/@orkestrel/sqlite/dist/src/server/index.js`, `relation` is `node_modules/@orkestrel/relation/dist/src/core/index.js`. Every line number refers to the installed built file. `M` is rows matching the filter, `N` is rows in the table, `P` is the page size.

The `@orkestrel/sqlite` and `@orkestrel/indexeddb` packages are thin wrappers over `node:sqlite` and the IndexedDB API. The drivers that implement `DriverInterface` live inside `@orkestrel/database`: `createSQLiteDriver` in `sqlite-driver` and `createIndexedDBDriver` in `idb-driver`. The audit of "the sqlite driver" and "the indexeddb driver" is therefore an audit of those two classes plus the wrapper capabilities they leave unused.

## Driver contract

`DriverInterface` (dts 723-745) extends `StorageInterface` (dts 1755-1808).

Required members:

| Member | Declared at | Role |
| --- | --- | --- |
| `open(schema)` | dts 723 area, `DriverInterface.open` | Builds tables and indexes from derived `TableSchema[]` |
| `close()` | `DriverInterface.close` | Releases the backend |
| `snapshot(tables?)` | `DriverInterface.snapshot` | Captures rows and returns a restore thunk |
| `read(table, key)` | dts 1759 | Point read |
| `write(table, key, row, options?)` | dts 1763 | Upsert one row |
| `insert(table, key, row, options?)` | dts 1768 | Insert one row, `CONFLICT` on duplicate key |
| `delete(table, key, options?)` | dts 1771 | Delete one row |
| `keys(table)` | dts 1775 | List every key |
| `scan(table)` | dts 1779 | Iterate every row in ascending key order |
| `clear(table)` | dts 1783 | Empty a table |

Optional hooks, with the core's behavior when the hook is absent:

| Hook | Declared at | Core fallback when absent | Fallback location |
| --- | --- | --- | --- |
| `records(table, input)` | dts 1787 | `applyQuery` over a full `#collect()` of `scan` (filter, then sort, in JS) | `Table.records` core 2849; `Table.count` core 2876 uses `filterRows` over `#collect()`; `Table.aggregate` core 2906 |
| `aggregate(table, op, column, input)` | dts 1791 | `computeAggregate` over `records` or over a full scan (`filterRows(#collect())`) | core 2904-2906; helpers core 748-791 |
| `stream(table, input)` | dts 1795 | `driver.scan(table)` iterated with JS `matchesQuery` and a `StreamPage` window | core 2981-2996 |
| `migrate(input)` | dts 1799 | A non-empty plan throws `DatabaseError` `MIGRATION`; a zero-step plan falls to `stamp` | core 2474-2492 and 2430 |
| `metadata()` | dts 1803 | `open` skips version reconciliation entirely when `metadata` or `stamp` is absent | core 2455 |
| `stamp(metadata)` | dts 1807 | Same as `metadata` (reconcile returns early); also the zero-step migration path | core 2455, 2491 |
| `transaction(scope)` | dts 735 area, `DriverInterface.transaction` | `snapshot()` of every table, run the scope against the root driver, restore the thunk on failure | core 2379-2420 (hook at 2379, snapshot at 2405) |

Facts that follow from the contract:

- No member counts rows. `Table.count` (core 2869-2878) therefore calls `records` and reduces over the guard. The contract has no `count` hook, and `aggregate('count')` is the only native count path. `Table.count` never calls it.
- No member writes a batch. `Table.set`, `add`, `update`, `remove` with an array run `#each`, one driver call per element in sequence (core 3002-3008).
- `records` receives `QueryInput` (dts 1506), whose type carries `limit` and `offset`, but `Table.records` strips both before the call (core 2844-2847) and slices in JS (core 2852-2854).
- `stream` receives only `{ conditions }` from `Table.#scan` (core 2981). It never receives `limit`, `offset`, or `order`, so a driver's native paging in `stream` goes unused.
- `IndexMap` (dts 909) and `TableSchema.indexes` (dts 2071) carry column-name groups only. There is no unique flag, no foreign-key reference, and no partial or expression index in the contract.
- `Cursor` (core 2539-2640) is built from `driver.keys(table)` plus one `read` per key (core 2969, 3010). It is not a native cursor.
- The core's own `MemoryDriver` implements `stream` (core 3414) but no `records`, `aggregate`, or `transaction`.

## The read guard

Why the guard exists:

- `Table` builds one contract per table from the declared columns (core 2790 constructor, `this.#guard = contract.is`) and applies it on every row that leaves the table: `records` (core 2851), `count` (2877), `scan` (`#cast`, core 2993), and each point read (`#read` through `#cast`, core 3010-3012, 3146-3148).
- Writes are already validated. `#put` and `#updateOne` call `#validate` (core 3025-3031, 3033-3046, 3128-3142) before any driver call, so a row written through `Table` satisfies the contract at write time. The guard on read therefore defends only against rows that did not come through `Table` under the current contract: rows written under an earlier contract, rows written by another process or tool, and rows a driver decoded lossily. SQLite's `decodeRow` drops a column whose stored value does not match its declared storage instead of failing (sqlite-driver 396-416, 489-497), so a row can lose a field silently on read. A migration does not revalidate stored rows (core 2455-2492 stamp only; `column.add` backfills nothing).
- `Table.count`'s TSDoc gives the reason in its own words (core 2858-2868): the guard determines the count so legacy invalid rows cannot make `count()` disagree with `records()`.

What it forces:

- `records` cannot pass `limit` or `offset` to the driver, because a driver cannot know how many of the first `offset + limit` rows will survive the guard. The core fetches every row matching the filter, guards each, then slices (core 2849-2854). Cost: `M` rows read, decoded, and guarded for a page of `P`.
- `count` cannot use `COUNT(*)`, because a count of rows is not a count of valid rows. Cost: `M` rows read, decoded, and guarded for one number.
- The invariant is already broken in one place. `aggregate` is documented as unguarded (core 2884-2896), so `aggregate('count', ...)` can disagree with `count()` on a table that holds an invalid row. The design already accepts one counter that ignores the guard.

Options weighed:

| Option | What it does | Keeps `count()` equal to `records()`? | Cost | Ruling |
| --- | --- | --- | --- | --- |
| Validate at write time with a typed schema | Already present (core 3128) | Only if no invalid row exists; it cannot cover legacy rows or out-of-band writes | None | Keep. Insufficient alone |
| SQLite `STRICT` tables and `CHECK` constraints | The engine rejects a value of the wrong storage class and can reject an enumeration violation | Yes for the classes it covers | SQLite only. Needs a table rebuild to add to an existing table. Cannot express `json` shape or nested contract rules. No IndexedDB equivalent, so the invariant would differ per engine | Reject as the primary mechanism. It can be added later as a defense in depth |
| Sweep or quarantine at open or migration | A one-time pass applies the guard to every row of a table and either removes invalid rows to a side store or reports them | Yes, if invalid rows are gone or the table is marked untrusted until they are | `O(N)` once per table per contract change, not per request | Adopt, as the verification step below. Do not auto-move rows: the package already states that existing malformed durable state fails closed and is "never treated as fresh, rewritten, or repaired automatically" (dts 723 area `DriverInterface` TSDoc) |
| Per-table trusted mark | Stores a verified flag per table, keyed to a contract fingerprint, in the metadata the drivers already persist (`_metadata` in SQLite, `__metadata__` in IndexedDB) | Yes while the mark holds | One metadata write per verified table | Adopt together with the sweep. A mark without a sweep proves nothing |
| Push paging down and guard only the returned page | Pass `limit`/`offset` to the driver and guard `P` rows | No. A page can come back short, offsets shift, and `COUNT(*)` counts rows the page loop drops | `O(P)` | Adopt only for a trusted table, with the loud-failure rule below. For an untrusted table it breaks agreement |

Recommendation: one path, the combination of a verification sweep and a trusted mark.

1. At `open()` after reconcile, and again after a `migrate`, the core checks each table's persisted mark against the table's current contract fingerprint (the compiled schema it already compares at core 2465). If the mark is absent or differs, the core scans the table once through `driver.scan`, applies the guard, and records the result.
2. If every row passes, the core persists the mark through `stamp`. The table is trusted. For a trusted table, `records` pass `limit` and `offset` to the driver, `count` calls the native count (`COUNT(*)` on SQLite, `store.count(range)` on IndexedDB when the plan is one range), and the guard runs on the returned page only (`O(P)` instead of `O(M)`).
3. If any row fails, the table stays untrusted and takes today's guard path (full candidate set, guard, JS slice). The core emits an event naming the invalid keys and offers an explicit `quarantine` call that removes them to a side table or store. Nothing is repaired automatically.
4. Count and records stay in agreement by construction: a trusted table contains only contract-valid rows (every write is validated at core 3128, and the sweep proved the rest), so the native count and the guarded page read one set. An untrusted table keeps the guarded count it has today.
5. A failure of the page guard on a trusted table is a corruption signal, not a filter. The core throws `DatabaseError` `DRIVER` or emits an `error` event and clears the mark. This turns an out-of-band write after verification into a visible failure instead of a silent disagreement.

What it costs:

- `O(N)` of guarded reads once per table per contract change, at open. A large table delays startup the first time after a contract change. The mark makes later opens free.
- One new persisted value per table in the existing metadata record, and a stored contract fingerprint. A driver without `metadata`/`stamp` (core 2455) cannot hold a mark, so its tables stay untrusted and keep today's behavior.
- A read-only database cannot persist the mark (`readonly` option, sqlite-driver 1679); it keeps the sweep result in memory for the session.
- An application that writes to the file outside `Table` can break the invariant between opens. The page guard in step 5 reports it.

Taverna's own rule makes the legacy case moot for its data. `AGENTS.md` (scaffold) states "Fleet packages and applications are greenfield: write no alias, wrapper, or migration for a shape or for data an earlier release produced" (scaffold `AGENTS.md:67`). The guard's legacy-row defense therefore has no consumer in taverna today, and taverna pays its price (`M` rows per count and per page) on every list.

## Ranked fixes

Cost model: `N` rows in the table, `M` rows matching the filter, `P` the page size. A paged list in taverna calls `count` and then `records` (`app/core/capabilities/helpers.ts:623-627`), so the two costs add. Taverna's read zone uses root storage and so reaches the native hooks (`app/core/capabilities/CapabilityRegistry.ts:157-160`); its write zone runs inside `database.transaction` (162-164, 235) and does not (item 4).

Ranking basis: the rows-read ratio between the current path and the native path, weighted by how many requests hit it.

1. **Native count.** Make `Table.count` call a native count and stop reducing the guard over `records`: add an optional `count` hook, or route `count` to the existing `driver.aggregate('count', ...)` (sqlite-driver 1774-1789) and to `store.count(range)`/`index.count(range)` (idb-wrapper 467-469, 544-545) on IndexedDB. Depends on the trusted mark.
   - Before: `M` rows read, decoded, and guarded (`N` when any clause is inexact). After: one aggregate row on SQLite; zero rows materialized on IndexedDB for a one-range plan. Every paged list pays it on top of the page read.
2. **Push `limit` and `offset` down and guard only the returned page.** `Table.records` passes paging in `candidate` (core 2844-2847) for a trusted table; SQLite already compiles `LIMIT ? OFFSET ?` (sqlite-driver 886-907); IndexedDB uses `getAll(range, offset + limit)` when `offset` is 0 and `openCursor` with `advance(offset)` otherwise (idb-wrapper 195-197, 377).
   - Before: `M` rows read, decoded, guarded, then sliced to `P` (core 2849-2854). After: `P` rows read on SQLite (the engine skips `offset` rows without decoding); at most `offset + P` on IndexedDB.
3. **Push down the exact clauses and refine only the residual; widen exactness.** Replace the all-or-nothing gate (`matchesQueryExactly`, sqlite-driver 274-278; `records` 1766-1772) with per-clause pushdown: compile the exact conditions into `WHERE`, run the inexact ones in JS over that candidate set. Add `starts` as an index-usable range (`col >= ? AND col < ?`) instead of `substr(...)` (sqlite-driver 728-745). Treat order on a text or optional column as pushable after the collation and `NULL` rules are documented. On IndexedDB, give `any` a plan (a set of `IDBKeyRange.only` reads) and give `starts` a plan through `rangePrefix` (idb-wrapper 287). This repairs relation loads, which are `any` conditions (relation 620-709).
   - Before: `N` rows read and decoded the moment one clause is inexact (an optional or nullable column, a text order term, `like`, a nested path), and `N_related` per relation per level on IndexedDB. After: `M_exact` rows, which is the rows matching the exact subset, and `|ids|` rows for an `any` over a key.
4. **Expose `records`, `aggregate`, and `stream` on the SQLite transaction capability.** Add the three hooks to `#capability` (sqlite-driver 2187-2200), each calling the existing method after `#requireTransaction(token)`.
   - Before: inside `database.transaction`, every `records`, `count`, and `aggregate` takes the core's `scan` fallback (core 2849, 2876, 2906): `N` rows read, decoded, and filtered in JS per query. After: the same row counts as items 1 to 3. Taverna's write zone runs every handler this way.
5. **Replace the whole-database snapshot fallback with a before-image journal.** For a driver without a `transaction` hook (IndexedDB), the core records the prior value of each key the scope writes or deletes and restores those keys on failure, instead of calling `snapshot()` over every table (core 2405; idb-driver 471-531).
   - Before: `Σ N_t` rows read per transaction over every table, and `Σ N_t` rows cleared and rewritten on rollback. After: `K` rows read (keys written) and `K` restored. Applies to every IndexedDB scope; taverna's browser store uses `createIndexedDBDriver` (`app/vue/factories.ts:48`).

Below the top five, in order:

- A batch-write member in the driver contract, so `set([...])` is one SQLite transaction or one IndexedDB transaction instead of one per row (core 3002-3008). Before: `K` commits. After: 1.
- A statement cache in the SQLite driver; every `read`, `write`, and `records` prepares a fresh statement (sqlite-driver 1768, 1950, 1960).
- Taverna-side: set `journal_mode = WAL` and a `timeout` through the driver's `pragmas` and `timeout` options (`app/server/factories.ts:139,143,146,150`). No package change is needed.
- Taverna-side: declare filter and order columns required (non-optional, non-nullable) wherever the domain allows, and declare an index on every foreign-key and filter column through `createDatabase`'s `indexes` option. Under today's gate, one optional filter column forces a full read. Which taverna columns are optional is unconfirmed (see the next section).
- Unique indexes and `REFERENCES` in the contract and in `schemaToTable`/`schemaToStore`, and an FTS5 index kind for text search. Today `like` over `N` rows is the only text search.
- `Model.link` and `Model.unlink` as single atomic operations (relation 523-563).
